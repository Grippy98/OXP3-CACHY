### Relevant implementation choices

The fork adds GTA handling for Social Club's auxiliary DXGI factories/windows, keeping their swapchains native while the game uses XeFG. It also changes Streamline initialization locking/loader ordering. Those source changes were reviewed for this integration. Although the release originates from a FreeFG fork targeting another GPU, this setup loads the **official native Intel libraries**. No FreeFG replacement DLL is installed and its vendor-library-specific pacer path is inactive. This is a selected compatibility build, not a claim that every newer upstream nightly is worse.

GTA's original combined `amd_fidelityfx_dx12.dll` remains at the game root. A copy named `OptiScaler/gta-stock-ffx.dll` is explicitly selected through `[Libraries] FfxDx12Path`; its observed hash is `12a5081257ec95b0b53ad51b4a87fb3c03f97fe0bbb59f9496968f8d50ef93a6`. Standalone modular AMD D3D12 loader/SR/FG providers are quarantined at both root and support locations, because OptiScaler otherwise prioritizes them independently of the main-library override. `FfxDx12SRPath`/`FfxDx12FGPath` remain auto. The copy avoids ambiguous reuse of the game module already hooked for input calls.

Native-context hot swapping is enabled, native FSR/FidelityFX inputs feed XeSS SR output, and both DXGI/Streamline spoofing are disabled. Factory wrapping and the simulated waitable-object workaround remain disabled. The short owner-confirmed SDR configuration uses native FSR-FG input, XeFG output and `InterpolationCount=1`, with the manual RenderUI workaround described below. The current short-test HDR/SR profile uses the official per-game vkd3d-proton 3.1 Core while retaining the original system32 D3D12 loader, private Mesa 26.3 and the private WSI candidate. It disables FG explicitly: `[FrameGen] Enabled=false`, `FGInput=nofg`, `FGOutput=nofg`, with the game's Frame Generator Off. Two cold starts reached Story Mode with fresh XeSS SR initialization and HDR active; combined FG remains unresolved. The exact configuration is in [README](README.md#gta-v-enhanced-setup).

The new repository `gta-launch.sh`/`gta-launch.py` helper has unit-test validation only; the hardware results here used the existing device wrapper, so equivalence has not yet been established on the device. Its intended profile defaults to private package 20261104/Mesa 26.1 and replaces conflicting DXGI override entries while retaining other Wine rules. Its default preserves the SDR WSI-off workaround; `--hdr` selects the private WSI layer described below. It edits no game files, INI or Steam settings. The shared launcher exposes the shim directly, merges the `VK_EXT_descriptor_buffer` and `VK_KHR_present_wait2` exclusions, and leaves the 20261018 default untouched for old shortcuts. Its inspection whitelist includes WSI flags and the private implicit-layer paths. No prefix DLL copying, ControlLib override, Proton hook, session environment or service is used.

### HDR/SR progress with a per-game vkd3d Core

The [GTA Enhanced HDR integration](../gta-enhanced-hdr/README.md) combines RenoDX, the official vkd3d-proton 3.1 Core and a private Gamescope 3.16.25 WSI event-queue backport. The private WSI patch isolates callback dispatch and preserves the older Gamescope interface; it is retained in the tested profile, but its necessity is unproved and stock WSI has not been qualified for this exact combination. The separate folder documents the private build, source pins and rollback without replacing system Gamescope.

The HDR chain retains OptiScaler's `dxgi.dll`. `[Plugins] LoadReshade=true` loads `ReShade64.dll`, the ReShade 6.8.0 full-addon loader, which loads the separate RenoDX GTA addon. RenoDX supplies HDR10. An earlier private-WSI-only Story pass looked correct, but later identical-profile cold starts froze; that is historical context rather than the current qualification.

The narrower synchronization lead was vkd3d-proton's dropped duplicate fence-event registration. Upstream [49a1e2c](https://github.com/HansKristian-Work/vkd3d-proton/commit/49a1e2c7098f4646374458b9a8fbc7c0d0b5ff3d) preserves every registration and is included in official 3.1. The [Core-only guide/installer](../gta-enhanced-hdr/vkd3d/README.md) stages only the pinned x64 `d3d12core.dll` beside GTA; the original system32 D3D12 loader remains so ReShade's device hooks still apply. The [source manifest](../gta-enhanced-hdr/vkd3d/source-pins.json) records the release/archive/Core hashes and exact loader-interface compatibility basis. Installing the full release DLL pair in the game directory had bypassed ReShade device interception and left HDR inactive; it was not an HDR-fix pass.

With only the new Core installed, private Mesa 26.3 selected and the private WSI candidate retained, ReShade/RenoDX initialized on D3D12, Gamescope reported application HDR and fresh XeSS SR 2.0.2 initialization reached Story gameplay. The owner said it worked. After restoring FG Off from a flickering native-FSR-FG test, a second cold start returned to Story. This is short-session HDR/SR validation; no controlled-performance, long-play, or combined HDR+FG claim is made. The comparison does not independently isolate the need for Mesa 26.3 or the WSI backport.

The repository's `gta-launch.sh --hdr` helper remains unit-tested only; these hardware observations used the existing device wrapper. Its intended launch command is:

### Driver-change settings resets

Changing the selected Mesa driver or reported GPU identity can make GTA reset SR and FG to Off. After a change, check the live menu and reapply the intended settings; a saved `ResScalingType=0` or `FrameGenType=0` is not an SR/FG test. Confirm actual SR evaluation/dispatch in the running game as well as presentation/HDR feedback. A successful Story launch without those checks must not be counted as XeSS compatibility evidence.

### Reproduce the historical package

These helpers still build the old pinned 20261018 combination, not the current prebuilt release. Use a fresh Linux x86-64 environment with a C/C++ toolchain, Git, Meson, Ninja, Mesa's ANV dependencies (LLVM/Clang/libclc, SPIR-V tools/translator, glslang, libdrm, Wayland/X11/XCB, expat, zlib, zstd and libelf development files), Python 3.12+, Mako, packaging, PyYAML and PLY. ## Mechanism and compatibility boundary

The shim answers Intel D3D extension queries and records XeSS CM kernels as placeholder D3D12 shaders. Patched ANV recognizes those placeholders, invokes the private Intel compiler, loads the resulting native kernels and reconstructs their resource bindings from vkd3d-proton's descriptor layout. This is a community userspace implementation; it does not add an Intel Windows kernel driver or a Linux display-driver fix.

The Mesa series adds native-kernel injection, optional developer diagnostics, Xe2 large-GRF handling, and a Mesa 26.3 fix selecting the older shader compiler for affected divergent-barrier shaders. The latter is a separate Mesa compatibility change. The descriptor reconstruction requires the classic vkd3d path. The current launcher merges `VK_EXT_descriptor_buffer` and `VK_KHR_present_wait2` into any existing disabled-extension list; the latter also follows the newer upstream FG compatibility requirement. It also sets `force_vk_vendor=0` so Mesa's per-game vendor hiding does not prevent the Intel extension path from being selected.

Keep this runtime private and per game. The launcher selects only the child process's 64-bit ANV manifest, preserves other driver selections and 32-bit Intel manifests, and passes the shim directory through `INTC_ALT_DRIVER_EXTENSIONS_PATH`. Galactic Racer reached its main menu under Proton Experimental `experimental-11.0-20261014-x86_64` with the private runtime loaded and the intended environment. Earlier Steam-selected Proton Hotfix `hotfix-20261007-x86_64` trials established loading but did not complete startup during observation. GE-Proton behavior is not covered. Steam's runtime container can relocate manifests, so inspect the final game's environment and mapped libraries rather than relying solely on the launcher's pre-execution printout.

The launcher does not write a system/session environment, replace installed Mesa, patch Proton, or copy a DLL into the game or prefix. Gamescope and unrelated applications retain their existing driver selection. The game's XeSS runtime can create kernel metadata in its prefix and compiled kernels in the user's cache. [README](README.md) gives the manual configuration and rollback; no automatic Steam configuration installer is provided.

## What has been established

STAR WARS: Galactic Racer, AppID `4078430`, contains XeSS `2.0.2.68` and XeFG `1.3.1.78`. Its actual Wine process mapped both private ANV and the rebuilt shim, and retained the intended environment. A fresh community canary was written, and the initial super-resolution trial compiled 30 CM kernels without failures. The Intel compiler disassembled a convolution kernel to 96 DPAS instructions; its native code matched the game-generated CMK cache byte-for-byte. This establishes generated XMX code, rather than a precise frame-rate or execution result.

The game subsequently reached its title, first-run screen and main menu under Proton Experimental `experimental-11.0-20261014-x86_64`. The owner then reported that 4K was difficult to play at roughly 40 FPS, while 1080p felt good and showed roughly 80 FPS. This establishes a positive subjective gameplay result at 1080p; it is not a controlled comparison or an attribution of the reported frames to XMX or XeFG.

The current saved selections are 1920×1080, XeSS Balanced, `Current3PAAUMode=XeSS`, `CurrentFrameGenerationProvider=XeFG`, `XeSSFGMode=On4x` and `bXeLLMode=True`, with game HDR off. The first selection was 2×, but the owner subsequently changed settings. The owner identified the reported counter as Steam/MangoHud's performance overlay. The multiplier active at that time and whether the overlay counted generated frames have not been established; the report therefore does not establish a base rendering rate or a 2×/4× gain. The running process still mapped private ANV and the shim. Fresh `libxess_fg.dll` callers were observed, and 114 kernels compiled successfully with no recorded compilation failure. No recent GPU hang/reset was observed during this check.

Earlier Hotfix trials with normal XMX, private-driver/generic fallback and a stock control had not completed startup during observation; the stock control also showed continuing CPU/shader-cache work. Reaching the menu later under Experimental does not, by itself, isolate the earlier delay to Proton or XMX.

These observations establish loading, compilation, generated matrix ISA and an owner-accepted 1080p gameplay result, not completed XMX dispatch or controlled SR/FG correctness. WaveSize-64 compute-pipeline rejections appeared in both private and stock logs; they can be optional variants and have not been established as the cause. A separate [upstream Galactic Racer report](https://github.com/ValveSoftware/Proton/issues/10228) describes similar startup symptoms on other hardware, without establishing an Intel solution. The canary is written when the driver recognizes a placeholder during pipeline compilation. It does not dispatch a correctness workload. The upstream kernel checker checks static filenames and file sizes, not dynamic-cache execution. The 45 current launcher/compiler/profile tests establish environment and argument behavior, driver/shim selection, compiler hashes and extraction, and early failure for absent private HDR layer files. They cover both SDR and HDR WSI profiles, mapping-based home/override paths, preservation and deduplication of other layer paths, complete removal of the WSI-disable variable, and literal child arguments. None executes the game or GPU. The saved shim build helper reproduced the installed DLL hash, and the compiler helper unpacked the real pinned DEBs in an isolated offline check. For Galactic Racer, **completed XMX dispatch, controlled SR/FG correctness, performance comparisons and HDR remain unverified**; GTA's newer short HDR/SR passes with Core 3.1 and separate unresolved FG paths are described above.

## Experimental limits

The implementation depends on specific Mesa, vkd3d-proton, XeSS and compiler details. It infers the resource heap, push-constant layout and sampler selection rather than using a public Vulkan ABI for CM injection. Its native-kernel metadata and payload handling are not a general validated kernel-loading interface. A new game library, Proton update or unsupported kernel layout can therefore compile yet produce incorrect output or fail at runtime. Pin the complete tested combination and repeat validation when it changes.

Compilation failure can leave a placeholder in the current launch; generic fallback normally applies on a later launch. A working canary does not guarantee that every kernel compiled or that resource bindings are valid. Keep developer overrides such as self-test bypass, ignored failures, forced feature answers and dispatch modification out of normal launch settings.

Community reports distinguish native XeSS frame generation from adding it through OptiScaler. The latter introduces separate swapchain hooks, with reported HDR crashes in one tested game. Begin with the game's native integration. XeLL uses its cross-vendor application-side pacing; Windows driver timestamp/latency support is not supplied. Additional presented frames are not an equivalent increase in simulation rate or a demonstrated reduction in input latency.

## Hardware validation

1. Keep the accepted display configuration and start in SDR. Hold resolution, scene, quality, power limit, frame cap and Proton version constant; disable dynamic resolution for comparisons.
2. Confirm the final game process maps the private driver and shim. Check the fresh canary and compilation results, then correlate SR/FG library callers with injected kernel hashes and actual dispatches. Target-matching ISA inspection for DPAS strengthens the XMX attribution; compilation alone does not establish it.
3. Test XeSS super resolution with FG off. Compare the private driver with `--fallback` against the same private driver in normal mode, using warm caches. A separate stock-driver baseline is useful, but changing Mesa/Jay at the same time cannot isolate XMX's contribution.
4. Enable native XeSS frame generation at 2×, then higher multipliers individually. Distinguish simulation cadence from presented cadence and inspect moving edges, disocclusion and UI for black, repeated, unstable or corrupted frames. Obtain the owner's visual confirmation.
5. Exercise cold/warm caches and failed-compiler recovery, then test HDR separately. Check game stability and GPU-reset reports, followed by dock/undock and resume. No VRR changes are required by this module.
6. Remove the per-game launcher and confirm the original driver path and game behavior return. Preserve the normal game prefix and Proton installation throughout.

Until those checks complete for a specific game and configuration, describe this as an experimental integration, not a general XMX/XeFG compatibility or performance result.
