# Xbox Wireless battery discovery and honest battery levels

**Status: built, installed and visually confirmed with one controller.** The implementation is a Controller Tools source patch, not a kernel or `xone` change. Source review and synthetic tests must be distinguished from the remaining live checks described below.

## Why Controller Tools 2.0.2 misses this device

Controller Tools 2.0.2, pinned at [`dcc05d953679c30b81ea3fb94a920af42fa3b44e`](https://github.com/jfernandez/ControllerTools/tree/dcc05d953679c30b81ea3fb94a920af42fa3b44e), reads several controllers through HID interfaces and uses a USB/udev fallback for Xbox. Its fallback accepts any Microsoft USB vendor ID as a controller, then assigns a synthetic 100% and charging state. A wireless receiver is itself a USB device, but its paired gamepads and batteries are separate GIP clients. Treating that receiver as a wired controller loses the actual battery and conflates one adapter with potentially several controllers. [USB enumeration](https://github.com/jfernandez/ControllerTools/blob/dcc05d953679c30b81ea3fb94a920af42fa3b44e/backend/src/api.rs#L181), [synthetic state](https://github.com/jfernandez/ControllerTools/blob/dcc05d953679c30b81ea3fb94a920af42fa3b44e/backend/src/api/xbox.rs#L45).

The original frontend also assumes numeric capacity and distinguishes transport using only a Bluetooth boolean. Its Microsoft-specific display rule suppresses percentages outside Bluetooth. These assumptions do not represent an Xbox Wireless connection with a coarse battery level. [Original presentation](https://github.com/jfernandez/ControllerTools/blob/dcc05d953679c30b81ea3fb94a920af42fa3b44e/src/components/Controller.tsx#L25).

## What the driver actually knows

xone 0.5.8 is pinned at [`f2aa9fe01103d7600553b505b298ff0bd47ff280`](https://github.com/dlundqvist/xone/tree/f2aa9fe01103d7600553b505b298ff0bd47ff280). Its implemented GIP status packet uses two bits for battery level and maps them to Low, Normal, High and Full. The driver exposes `POWER_SUPPLY_PROP_CAPACITY_LEVEL`, status, device scope and model name. It does not expose `POWER_SUPPLY_PROP_CAPACITY`. [Packet fields and decode](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/bus/protocol.c#L23), [level definitions](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/bus/protocol.h#L25), [power-supply properties](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/driver/common.c#L13).

The supply is registered under its individual GIP client, with a `powers` link to that client. Its input identity is also below that client. Consequently the correct battery/controller relationship is available in sysfs without opening the controller, querying raw GIP or changing the driver. [Registration](https://github.com/dlundqvist/xone/blob/f2aa9fe01103d7600553b505b298ff0bd47ff280/driver/common.c#L46).

UPower may expose a compatibility percentage estimated from these categories. That does not turn Normal into a measured 55% or provide a true state of charge. UPower tells frontends to prefer `BatteryLevel` for coarse reports. This patch reads the original categories directly. No supported finer measurement was established from this GIP status path; that is not a claim that every possible undocumented firmware command is incapable of providing more information. [UPower semantics](https://upower.freedesktop.org/docs/Device.html).

## Implementation

The patch adds a read-only xone backend alongside the existing controller backends:

1. Enumerate power supplies and canonicalize their paths. Resolve the containing client bound to `xone-gip-gamepad`; stop at a differently bound device rather than climbing to a receiver or sibling.
2. Read the input name, vendor/product IDs and optional identity only from that same client's `input` children. Validate that resolved paths remain within the client. Use the canonical client path as the internal identity so identical models without serials remain distinct.
3. Read that supply's status and capacity level. Missing/unrecognized attributes become unknown; disappearance or unbinding removes the client from the snapshot. One unavailable client does not discard other clients.
4. Identify Xbox Wireless transport through the known Microsoft receiver ancestors. Keep the controller's own IDs rather than substituting the adapter's IDs. Exclude receivers from the ordinary wired-controller fallback and suppress a duplicate USB fallback when a real GIP record already exists under that USB device.

The resulting JSON uses `capacity: null`, `batteryLevel: "normal"` and `connectionType: "wireless"` for a typical coarse wireless report. `bluetooth` remains false. Internal client paths and serials are not serialized into frontend responses. Controllers providing actual numeric capacity retain it through the nullable capacity field.

The wired Xbox fallback now admits known controller product IDs, not every Microsoft USB device. Without battery telemetry it reports unknown capacity/status instead of inventing full charge. Existing Xbox Bluetooth probing is retained; its legacy failed-read zero remains an ambiguity and is displayed neutrally when the status is unknown.

Frontend presentation gives coarse levels precedence over numeric capacity, including any contradictory compatibility estimate. It shows readable level labels, corresponding battery icons and an explicit Xbox Wireless connection indicator. Missing values are neutral; a valid numeric zero remains 0% for backends where zero is a real reading.

Low-battery notifications use the same distinction. A discharging coarse **Low** triggers a level-based message; other coarse categories suppress numeric-threshold alerts. Numeric-only controllers retain the existing below-20% rule. The frontend now accepts browser WebSocket `message` events; the old code checked for `text` and discarded them. A dismount cleanup closes its socket and cancels retry timers to avoid duplicate subscriptions after plugin reload. Notification preferences, polling and per-controller rate limiting remain in place. Reconnects may change GIP client identity, so the client path is a connection identity rather than a permanent physical-controller identifier.

## Validation and remaining limits

The patch includes synthetic backend fixtures for separate same-model clients, missing/malformed attributes, disconnect/unbind behavior, unrelated power supplies, path association, receiver exclusion and wired fallback. Serialization and notification tests cover null capacity, category precedence and numeric thresholds. Frontend tests cover coarse labels/icons, unknown values, numeric zero, charging presentation and transport labels. The Linux backend build and 13 applicable Rust tests passed on the OXP3; 10 frontend/notification tests and TypeScript checking passed. One pre-existing upstream settings test failed because it assumes a read-only service creates and writes a settings file, and is explicitly excluded by the build helper. The xone discovery, serialization and notification tests all ran.

The installed Rust process was replaced through Decky's plugin-only reload. Its API returned one real Xbox controller with its own `0b12` product ID, wireless transport, null numeric capacity and `Normal` battery, matching that controller's sysfs supply. The receiver's fabricated charging entry disappeared; the built-in wired controller remained listed with unknown battery. The frontend was built and deployed together with the backend. Decky registered the updated frontend, including its new notification cleanup, and the user confirmed that the controller shows `Normal`. Two real connected controllers still need confirmation. Unplug/reconnect and controller power-off should remove/recreate only the relevant entries. A low-battery fixture verifies policy; it does not replace a physical low-battery notification test. PlayStation, Nintendo and Bluetooth regression checks are also separate from xone fixture coverage.

The read path makes no battery, LED, pairing or input writes. It does not create an estimated percentage file, overlay sysfs or alter UPower. Reported categories are limited by the controller, its firmware and the driver. Numeric charge, remaining runtime and charging detection cannot be inferred when no such telemetry is available.

## Build, deployment and upstreaming

[patches/0001-xone-wireless-battery.patch](patches/0001-xone-wireless-battery.patch) targets the exact Controller Tools source pin above. `build.sh` prepares a separate checked-out source tree at `build/controller-tools-xone-battery` and places a complete payload under its `package/ControllerTools` directory. Keep the included [GPLv3 license](LICENSE) with redistributed source and plugin payloads. Do not copy build outputs or private runtime settings into this fixes folder.

Deploy and restore the Rust backend and frontend as a pair, with a complete payload backup outside Decky's plugins directory. Decky 3.3.0 provides the plugin-only route `loader/reload_plugin`, called with the metadata name **`Controller Tools`**, not the directory name. It stops the old backend, starts the replacement and dispatches a frontend reload; a Steam restart is unnecessary. Its response acknowledges queueing, so verify completion separately. [Reload handler](https://github.com/SteamDeckHomebrew/decky-loader/blob/67196adfa9b299f20dfb0cc932e88a169417b7d5/backend/decky_loader/loader.py#L235), [backend replacement](https://github.com/SteamDeckHomebrew/decky-loader/blob/67196adfa9b299f20dfb0cc932e88a169417b7d5/backend/decky_loader/loader.py#L166), [frontend reload](https://github.com/SteamDeckHomebrew/decky-loader/blob/67196adfa9b299f20dfb0cc932e88a169417b7d5/frontend/src/plugin-loader.tsx#L414).

An upstream contribution should include the discovery, nullable/category model, honest wired fallback, presentation and notification tests together. It should preserve category reporting rather than manufacturing percentages. Additional receiver IDs or altered xone layouts need explicit source and test coverage; a plugin update requires a fresh applicability check.
