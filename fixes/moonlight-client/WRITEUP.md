# Moonlight implementation and upstream direction

## Problem and source boundary

A handheld can use different display sizes and refresh rates when docked and undocked. Moonlight's saved fixed resolution/FPS and a single bitrate can require repeated adjustment. Separately, Linux Intel HEVC 4:4:4 decode support does not by itself guarantee that the decoded surfaces can reach the renderer: the packed DMA-BUF layout also needs a compatible import path. DualSense waveform feedback additionally needs a compatible host protocol and a client renderer; ordinary SDL rumble and adaptive-trigger support do not supply that path.

The integrated implementation lives in [Grippy98/moonlight-qt at `9003439366f8c566d938b5625bad1e2e6f8dc11c`](https://github.com/Grippy98/moonlight-qt/tree/9003439366f8c566d938b5625bad1e2e6f8dc11c), on branch [feature/oxp3-dualsense-waveform](https://github.com/Grippy98/moonlight-qt/tree/feature/oxp3-dualsense-waveform). This collection contains documentation and a manual menu entry only. It carries no duplicate client source, adapter patch, application binary, profile or hardware capture.

Its base is [Nonary daily 196, `76ee502543a2305afe06205644611975e3636737`](https://github.com/Nonary/moonlight-qt/commit/76ee502543a2305afe06205644611975e3636737), with waveform-capable common-c pinned at `3f9c009fe01db573cd29c1f286db5b7fa8a922fc`. The existing OXP3 display/bitrate/private-import work is ported from [the earlier `bd00969` client](https://github.com/Grippy98/moonlight-qt/commit/bd009697190f2c1e012afaeaa7ed1ef4ea27170a), which originally used upstream Moonlight `dc92b6d2f361064d3e9e53ce5de92f611db77220`. Submodules remain fixed by the new checkout's gitlinks. Build and private-profile rollback instructions are in the [README](README.md) and pinned [client guide](https://github.com/Grippy98/moonlight-qt/blob/9003439366f8c566d938b5625bad1e2e6f8dc11c/docs/oxp3-cachyos.md).

## Bluetooth DualSense waveform path

The original OXP3 preview supported ordinary rumble and adaptive triggers, but had no waveform renderer. The Nonary base adds a versioned control-channel waveform extension and a Linux Bluetooth renderer using the pinned SAxense packet format. The host supplies native actuator samples; the client worker performs bounded queueing, resampling and output to the kernel-verified physical controller's `hidraw` path. A virtual Xbox controller from Steam Input cannot substitute for that physical association.

The Bluetooth output format is signed 8-bit stereo at 3 kHz. This transports native waveform effects rather than approximating them as two motor amplitudes, but it is not a bit-perfect copy of the 48 kHz USB haptic path. Controller speaker and microphone streaming are outside this Linux extension. The kernel HID driver and SDL continue to provide input and non-waveform effects; the renderer must coexist with adaptive triggers, ordinary rumble after PCM idles, reconnection and teardown.

On Windows, Vibepollo needs its optional DualSense USB audio/haptics component and a backend that exposes the virtual controller's audio endpoint: explicit `usbip_ds5`, or Automatic PlayStation selection when that transport is available. A conventional virtual DualSense can expose buttons and adaptive triggers while still lacking waveform audio. USB/IP runs locally on the Windows host; the OXP3 receives waveform samples over the streaming control connection. Native game support and any host Steam Input override are separate from the client's Steam Input override. Keep both overrides scoped to the relevant app rather than disabling controller mapping globally.

The existing OXP3 Steam shortcut was found to launch the Flatpak, while the custom preview had a separate desktop launcher. The shortcut was retargeted through Steam's own APIs to the native preview launcher, with empty launch options and Steam Input disabled for Moonlight only. A fresh native app-details subscription confirmed the executable and override; a cached JavaScript detail object did not refresh itself. The shortcut's original executable/start directory/options and controller override remain in a private backup, and the original Flatpak remains installed for rollback. InputPlumber's existing OXP3 composite does not contain the connected DualSense, so removing the built-in controller integration was unnecessary.

See the [renderer validation guide](https://github.com/Grippy98/moonlight-qt/blob/9003439366f8c566d938b5625bad1e2e6f8dc11c/tests/haptics/README.md), [SAxense provenance](https://github.com/Grippy98/moonlight-qt/blob/9003439366f8c566d938b5625bad1e2e6f8dc11c/third-party/saxense/PROVENANCE.md) and Vibepollo's [Windows host instructions](https://github.com/Nonary/Vibepollo/blob/master/docs/windows-dualsense-haptics.md). A client log reporting backend attachment and capability `0x8000` is a useful negotiation check, not proof that a game delivered a physical effect.

## Native resolution and FPS

Two independent saved booleans select display-following resolution and FPS. Fixed/manual values stay saved as fallback values. The session resolves Native once at each connection start, before choosing its automatic primary bitrate. It does not change the local display mode or renegotiate an already-running stream.

Under Gamescope, the desktop display may describe the virtual game-sized surface. A read-only DRM query enables atomic property access and looks for a single active physical output, ignoring a connected but disabled built-in panel. Multiple active outputs or incomplete/inaccessible DRM information fall back to the selected desktop display. Invalid discovery retains the corresponding fixed preference. Current timing provides the refresh rate, rounded to the nearest integer required by the streaming protocol.

The client cannot guarantee that a host accepts the requested dimensions, codec or rate, and it does not provision a host virtual display. Detection tests and a successful docked production-object probe support the selection logic; they do not establish physical undock/reconnect behavior or a game's pacing.

## Network-aware bitrate

The checkbox enables a second saved bitrate. Selection uses the socket route to the streaming host at connection start. Only positively identified non-VPN Ethernet selects the primary preset; Wi-Fi, VPN and unknown routes select the Wi-Fi preset. Ethernet can therefore be selected while an unrelated Wi-Fi connection remains up. This does not measure available throughput or continuously adapt the rate.

The shared runtime policy keeps explicit primary/Wi-Fi values intact. Conventional-codec automatic primary defaults use the resolved dimensions, FPS and chroma, then clamp to 500–150000 Kbps, or a 500000 Kbps maximum when unlocked. The Nonary base's PyroWave-specific automatic rate is preserved rather than capped by compressed-codec limits. Slider changes and `--bitrate` select a manual primary rate. `--wifi-bitrate` enables the separate preset; `--bitrate` alone disables a saved network-aware selection. A host fallback from 4:4:4 to 4:2:0 recomputes only an automatic primary rate, preserving manual and Wi-Fi values.

CLI Native and fixed options update their respective setting independently; the last conflicting option of each type wins. Pure policy tests exercise route classification, manual values, selected presets and automatic bounds through the same helpers used by the client.

## Opt-in Intel packed-surface import

The [candidate and technical writeup](https://github.com/Grippy98/moonlight-qt/blob/9003439366f8c566d938b5625bad1e2e6f8dc11c/contrib/intel-packed-yuv444/WRITEUP.md) target libplacebo **v7.360.1**, commit `cee9b076f2c63104ccfd497fa79c39a867293ec4`. Moonlight compiles that library's header-only FFmpeg adapter, so rebuilding this object against a private patched header is sufficient. The build checks the exact shared-library version and input-header hashes, leaving installed headers and the shared library unchanged.

For supported Vulkan imports, packed XYUV uses a bit-identical BGRA8 alias, and Y410/XV30 use RGB10A2 aliases. Channel mappings retain YUV interpretation, bit depth and color metadata. Known unsupported layer/plane layouts and failed imports are refused. The candidate preserves VAAPI decoding and GPU rendering; it adds no streaming-frame CPU download or runtime software-decoding fallback. It still relies on FFmpeg/driver descriptor validity as the original adapter does.

Regression coverage includes packed descriptor mappings, unsupported layouts, failed-import cleanup, source immutability, GPU channel/color arithmetic and software test oracles. A separate offscreen Intel hardware probe forces VAAPI decode and direct DMA-BUF/Vulkan import for 8-bit and 10-bit HEVC 4:4:4. The CPU reference is a test oracle only. Successful small offscreen packets establish interoperability for those layouts; they do not prove visible HDR presentation or full-resolution streaming throughput.

## Validation limits and rollback

The integrated Native tests, 61 bitrate checks, six private-launcher tests, QML parsing and haptics renderer suite passed. The full Linux Qt HDR/4:4:4 client built and was installed as the native preview, with a private backup of the original complete runtime, profile and Steam shortcut metadata. The installed haptics-license command prints the pinned SAxense source/license material.

A controlled local probe attached the actual Bluetooth PS5 controller and sent a short left-then-right waveform sequence. The owner confirmed both distinct physical effects. A Windows desktop stream through the updated Steam shortcut then opened the physical Sony Bluetooth HID device and announced the PS5 controller with capabilities `0x80fb`, including waveform support. Bluetooth reconnection after the physical controller's firmware update was also detected and advertised.

During subsequent gameplay, a bounded passive Bluetooth check observed CRC-valid SAxense waveform output reports with nonzero samples on both actuator channels. These are distinct from the conventional rumble output reports observed on the same connection. The live client also dispatched repeated adaptive-trigger effects successfully. This verifies actual streamed waveform and trigger output to the physical Bluetooth controller, beyond backend registration or a synthetic local test. The owner's local left/right perception was confirmed separately; subjective gameplay feel and a full reconnect/stream-teardown regression remain separate checks. Raw captures, addresses and samples are excluded from this repository.

The existing paired host identity was retained, and the original Native/automatic-bitrate preferences were restored after the temporary connection test. Refreshing the saved host address is a private deployment detail, not a source default.

The earlier OXP3 client passed a native CachyOS build, production docked display-detector validation and real offscreen Intel import checks. Those results establish the original feature/prototype boundaries; they are not fresh display validation of this integrated build. Physical undock/reconnect, compositor HDR/swapchain negotiation, TV HDR signaling, 4K/144 Hz HDR/4:4:4 performance and gameplay pacing remain separate checks. No HDMI link, VRR or CEC support is implied.

The private launcher copies the installed Flatpak's configuration only when a preview profile is absent, preserving pairing identity and key casing. It initially changes only the two Native preference values. Private permissions, linked/unowned path refusals and argument forwarding are covered by launcher regressions. Later launches retain preview edits, and nothing is copied back. Quitting the preview and returning to the original Flatpak is the application rollback; restore any retargeted Steam shortcut and its per-app input override from the private backup. Selecting a standard build removes the adapter prototype from the comparison.

## Upstream targets and licenses

Native display selection, CLI/settings behavior and network-aware bitrate changes belong in Moonlight, with policy tests and platform fallbacks reviewed there. The packed import belongs in libplacebo's FFmpeg adapter; related primary reports are [libplacebo issue 282](https://github.com/haasn/libplacebo/issues/282) and [Moonlight issue 1512](https://github.com/moonlight-stream/moonlight-qt/issues/1512). The exact pinned adapter candidate should be reviewed/rebased for other libplacebo versions before broadening its build support.

Moonlight retains its [GPL-3.0 license](https://github.com/Grippy98/moonlight-qt/blob/9003439366f8c566d938b5625bad1e2e6f8dc11c/LICENSE). SAxense-derived packet sources retain their [MPL-2.0 notices and dual-distribution explanation](https://github.com/Grippy98/moonlight-qt/blob/9003439366f8c566d938b5625bad1e2e6f8dc11c/third-party/saxense/PROVENANCE.md); `moonlight --haptics-license` prints the embedded source and licenses. The candidate adapter patch retains [libplacebo's LGPL-2.1-or-later license](https://github.com/Grippy98/moonlight-qt/blob/9003439366f8c566d938b5625bad1e2e6f8dc11c/contrib/intel-packed-yuv444/LICENSE.libplacebo). Source, pins, attribution and reusable tests remain with the linked implementation; this entry makes no upstream submission or change to those licenses.
