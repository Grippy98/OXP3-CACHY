The checked device has BIOS 5.08, InputPlumber 0.81.0, Mesa/Vulkan 26.2.4 including 32-bit packages, and `mangohud-onex3` 0.8.4-3. MSR and MMIO sustained/short power limits are aligned. None of the pack's three games was found in the available Steam library. These facts establish applicability, not performance gains.

The headline Cyberpunk/FF7R comparisons start from SteamOS Mesa 26.1.2. The README itself attributes much of the gain to a newer Mesa/compiler, so those gains cannot be assumed over Cachy 26.2.4. RE4 reports a higher average but a lower 1% low, 72.5 to 70.5 FPS. Results are from one machine at 30 W in SDR and have not been reproduced here. [Reported results](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/README.md#L7-L24).

## Installer and launch-wrapper findings

### G01 — Updating the pack can break stock rollback

If no local DLL originally exists, install A creates one without a backup. Updating to B then saves A as `.oxp3-pack-bak`, treating the older patched DLL as the original. Revert restores A and deletes the installation journal. The installer records neither backup provenance nor original/installed content hashes, so revert can also overwrite a subsequent game update or user change. [Install:128–136](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/oxp3-game-pack.sh#L128-L136), [revert:224–243](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/oxp3-game-pack.sh#L224-L243).

The DLL pair is not replaced transactionally: backup/copy errors are unchecked and a partial failure can leave mixed or missing files while installation reports success. Revert erases its journal even after restoration failure. A safe adapter needs original-absence markers, original/installed hashes, staged pair replacement, checked operations and conflict-aware rollback.

### G02 — The checker executes native code; fallback is only a preflight

`--check` invokes `ctypes.CDLL()` on supplied drivers, which can execute native initialization code. It is not a passive way to inspect untrusted builds. Archive checksum verification is reached only on the installation path, after check/revert dispatch. [Driver check:105–111](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/oxp3-game-pack.sh#L105-L111), [dispatch:241–247](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/oxp3-game-pack.sh#L241-L247).

At launch, fallback checks whether the shared object opens and logs `pack=on` before the game executes. This does not establish Vulkan initialization inside Proton's runtime, successful presentation or correct gameplay. Installer-side `vulkaninfo` is useful but likewise does not establish those outcomes. [Runtime wrapper](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/oxp3-run#L6-L20).

### G03 — HDR is disabled and the off switch is not a stock baseline

Cyberpunk and FF7R force `PROTON_ENABLE_HDR=0` and `DXVK_HDR=0`; RE4 clears `VKD3D_DISABLE_EXTENSIONS`. The wrapper overwrites inherited variables, so placing a user's override before it does not preserve that choice. These SDR benchmark presets conflict with the current HDR use case. [Cyberpunk](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/games/1091500.conf.in), [FF7R](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/games/2909400.conf.in), [RE4](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/games/2050650.conf.in).

`OXP3_PACK=0` skips wrapper settings/custom ICD but leaves the replacement vkd3d DLLs installed and removes the wrapper's cache-path overrides. It cannot isolate total pack benefit; cold/warm cache differences also need control. [Comparison instructions](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/README.md#L98-L109).

### G04 — Topology detection needs better boundaries

The installer assumes `cache/index3` means shared L3, does not explicitly intersect with online CPUs, ignores current affinity/cpuset restrictions, and caches the result at install time. A reusable helper should read cache `level`/`shared_cpu_list`, intersect online and currently allowed CPUs at launch, reject ambiguous groups and preserve explicit user topology settings. The live 0–9 group makes this idea relevant; it does not prove a game benefits from losing four LP cores. [Detection:77–85](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/oxp3-game-pack.sh#L77-L85), [Linux CPU/cache attributes](https://www.kernel.org/doc/Documentation/ABI/testing/sysfs-devices-system-cpu).

The supplied Proton patch extends automatic affinity-derived Wine topology to x86; it does not itself set Linux affinity. The pack does not use that patch. Its explicit `PROTON_CPU_TOPOLOGY` option is already supported by the installed Proton, so an individual launch-option test can precede any maintained wrapper. [Proton patch](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/patches/proton/0001-proton-derive-WINE_CPU_TOPOLOGY-from-the-launch-affi.patch).

## Graphics changes

**Mesa 0001** narrowly reduces generic-write destination flushing to L1/L2 on Xe2+. Mesa 26.2.4 already has an analogous source-side optimization, which provides a rationale, but destination synchronization still needs correctness/CTS validation. No reproduced current-device bug establishes that this is required. [Patch](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/patches/mesa/0001-anv-use-L1-L2-flushes-for-generic-write-destinations.patch).

**Mesa 0002** moves buffer copies/updates onto compute and adjusts query/upload synchronization for the actual execution path. It targets Mesa 26.3's newer BLORP parameter API/helpers, absent from 26.2.4. It is not a drop-in patch for the installed driver. [Patch](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/patches/mesa/0002-anv-run-buffer-copies-and-updates-on-the-compute-pip.patch), [26.2.4 BLORP](https://gitlab.freedesktop.org/mesa/mesa/-/blob/mesa-26.2.4/src/intel/vulkan/anv_blorp.c#L162).

**vkd3d host-readback exemption** applies to every Mesa Intel driver without a version, generation or queue guard. Mesa 26.2.4's primary render/compute completion flush provides a credible rationale, but does not establish coverage for all ANV versions/queue paths. Removing an availability barrier requires synchronization/readback tests; host-coherent memory alone is insufficient. [Patch](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/patches/vkd3d/vkd3d-0001-treat-anv-as-implicitly-syncing-host-readback.patch), [upstream barrier](https://github.com/HansKristian-Work/vkd3d-proton/blob/0bb64c56/libs/vkd3d/command.c#L163), [Mesa completion handling](https://gitlab.freedesktop.org/mesa/mesa/-/blob/mesa-26.2.4/src/intel/vulkan/genX_cmd_buffer.c#L4174), [Vulkan synchronization](https://docs.vulkan.org/spec/latest/chapters/synchronization.html).

**FF7R shader stack** is available as a [source archive](https://github.com/kas5852/onexplayer3-steamos-setup/releases/download/game-pack-20261020/mesa-ff7r-src.tar.xz), SHA-256 `50a731fd5edaf2d3bae20a03fea7ac031684fb727a78cf93869d3fe0b8cfb948`. It contains much more custom code than the checked-in patches. Two source-level correctness concerns prevent treating it as a general safe compiler upgrade:

- `intel_nir_opt_atomic_branch.c:10–21,87–88,160–222` replaces selected atomics with ordinary loads and removes coherent access. Its comment acknowledges that arbitrary racing-memory ordering/linearization is not preserved. Hash selection narrows scope but does not prove the required access properties.
- `anv_shader_compile.c:241–252` can classify a phi selected by a divergent condition as uniform when both arms are constants. The related store check at 342–372 does not prove identical values across stores/control paths. The rewrite at 503–528 changes a flat integer varying into interpolated floats and reconstructs it by rounding. Different per-vertex IDs can therefore pass the stated guard and interpolate incorrectly. This is a general source-level counterexample, not a reproduction of corruption in the two whitelisted FF7R shaders.

The FF7R build remains a specialized experiment. The archive is a working-tree snapshot without Git history; no independently reproducible build recipe or binary-to-source correspondence was established. Checksums establish asset identity, not compiler correctness or reproducibility. The generated game archive also needs its component license materials preserved if repackaged. [Source/build table](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/README.md#L134-L143), [archive builder](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/game-pack/make-archive.sh).

## Linked Intel Decky plugin

**Advertised Intel GPU range is disabled:** the called setter returns `False` for Intel, despite being able to read xe frequency endpoints. This release cannot apply its proposed RE4 650–2200 MHz range. [GPU setter:133–142](https://github.com/kas5852/SimpleDeckyTDP-Intel/blob/a8a01f3550f4834d19a500107f7f8d57996e7930/py_modules/gpu_utils.py#L133-L142).

**Smart Boost is static caps:** 3.0/2.0/1.5 GHz selected from three base-frequency groups. It takes no snapshot; clearing caps writes `9999999` instead of restoring previous values. Partial failures can still mark completion. Unload/uninstall perform no hardware cleanup. [Caps:7–61](https://github.com/kas5852/SimpleDeckyTDP-Intel/blob/a8a01f3550f4834d19a500107f7f8d57996e7930/py_modules/smart_boost.py#L7-L61), [unload:276–283](https://github.com/kas5852/SimpleDeckyTDP-Intel/blob/a8a01f3550f4834d19a500107f7f8d57996e7930/main.py#L276-L283).

**A competing power writer:** it selects MMIO when available instead of synchronizing MSR/MMIO, writes every matching power constraint without named discovery/readback/rollback, and reapplies on profile changes, resume or polling. Its governor/EPP controls also change system-wide policy. Keep the accepted SteamOS Manager TDP backend; optional CPU controls should not write TDP. [Selection](https://github.com/kas5852/SimpleDeckyTDP-Intel/blob/a8a01f3550f4834d19a500107f7f8d57996e7930/py_modules/cpu_utils.py#L23-L80), [write path](https://github.com/kas5852/SimpleDeckyTDP-Intel/blob/a8a01f3550f4834d19a500107f7f8d57996e7930/py_modules/cpu_utils.py#L399-L414).

**Updater concerns:** a bare `ssl.SSLContext()` does not enable certificate/hostname validation by default; there is no artifact hash/signature check. The updater deletes the installed plugin before unpacking and returns an undefined variable. [Updater:29–74](https://github.com/kas5852/SimpleDeckyTDP-Intel/blob/a8a01f3550f4834d19a500107f7f8d57996e7930/py_modules/plugin_update.py#L29-L74), [Python TLS defaults](https://docs.python.org/3/library/ssl.html#security-considerations).

- **Gyro:** the patch and complete SSDT are unchanged from the prior audit. The installer still targets BIOS 5.09/InputPlumber 0.78, unlike this 5.08/0.81 unit; `--force` bypasses separate guards, while the fork launcher subsequently rejects newer stock InputPlumber. The current `-121` is a failed bus read, so an ACPI rename alone is not proven sufficient. Prefer an actual identification/resource investigation and current-driver correction; keep steering/drift policy separate. - **Telemetry:** the SteamOS 0.8.3 MangoApp build falls back on Cachy 0.8.4. Our backport already supplies actual PMT GPU temperature and wrap-aware power reporting. The new root service globally overlays synthetic counters onto kernel sysfs and executes a user-editable script as root. Optional CPU-core/package labels merit separate upstream work; replacing the accepted implementation is not justified. [Description](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/mangoapp/README.md), [service](https://github.com/kas5852/onexplayer3-steamos-setup/blob/66677eafecf1090dcd578c0a07597e79f876d462/oxp3-apply-fixes.sh#L858-L920).
- **DMC v2.20 downgrade:** this device loads v2.36, but the reported current internal-VRR ceiling has not been reproduced with the accepted kernel/runtime. The installer treats a differing compressed hash as newer firmware, overwrites any existing override without backup, and deletes it on revert. Consider controlled firmware comparison only if the relevant symptom returns. Use a structured exact-card WirePlumber/UCM correction only if that separate symptom is reproduced. ## How to evaluate independent additions

For CPU topology, keep Proton, HDR state, sustained power and cache warmth constant. Alternate repeated runs of the same scene and compare frametime distributions/1% lows as well as averages. Preserve the original launch options. A CPU-only cap tool needs exact snapshots, checked writes/readback, partial-failure rollback and restoration on game exit/disable/unload, with no competing TDP writes.

For graphics changes, use reviewed source, pinned build tools/dependencies, component licenses and isolated per-game selection. Validate Vulkan correctness, rendered output and performance separately. None of this source review establishes a new device performance result or justifies making the supplied bundle a default.
